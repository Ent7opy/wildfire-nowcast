## 1. Thesis adherence

The user-facing surface now matches the thesis materially better than it did 24h ago: the AOI page actually renders the polygon (MapLibre, fitBounds, FRP-scaled detection circles, attribution-correct demo basemap), the AOI/new page exposes a real three-tab create flow (paste, upload, draw — three of three, exceeding the SPEC "at least two" floor), the brief footer no longer leaks operator telemetry to the user (cost/latency/model are gone from app/dashboard/brief/[id]/page.tsx — only "Posted: ..." remains), and emails carry the four signed-token actions per lib/notify/footer.ts. Stage 8 authority-perimeter pre-fetch wires the load-bearing authority_perimeter field for North America from lib/ai/authority/fetch.ts, with build-without-blocking discipline (any source error returns null and the brief still ships). Stage 9 dispatchWatchConfirmed + backfillForNewAoi together close SPEC Flow 1 end-to-end so the 5-minute SLA is now structurally measurable. The thesis's biggest remaining gap is the same one the brainstorm surfaced honestly: fetchPriorEvents (lib/ai/generate.ts:404-) still queries only this DB's own aoi_events history — for a brand-new AOI on launch day, every brief's most thesis-load-bearing field will read "no prior events on file." The team has a research note on weather, no work on a real prior-fire dataset (MTBS, EFFIS, GlobFire), and the LLM cannot synthesize a Mati/Evia analogue from absent context. The brief is L1.7 now, not L1.5; it is not yet the thesis L2 sample paragraph, and ICNF (the Mediterranean-archetype perimeter source) is correctly blocker-listed but unfixed.

## 2. Flow coherence

Walking the post-Stage-9 cold-start: a newsletter reader lands on /, sees the canonical positioning line and one CTA. Sign-in via Clerk. /dashboard/aoi/new exposes the three-tab picker with name field reused across tabs. **First flow break I see: in the "Draw on map" tab the name input sits *above* the map and the user is told to double-click to save — but if the user draws first and types the name second, submitDrawn rejects with "Name is required." There is no debouncing between draw-completion and save; double-click saves immediately.** That is a genuine UX trap on a 5-minute cold-start path. Once an AOI is created, app/api/aoi/route.ts schedules dispatchWatchConfirmed + backfillForNewAoi via next/server's after(), the user is redirected to /dashboard/aoi/{id} (which now mounts the map, the freshness banner, the rules form, and a recent-briefs list), and within 60s the welcome email lands and within minutes the backfill either produces a brief or does not. **Second break, structural: SPEC US-1 acceptance is "first watch confirmed email in <=5 min on a clean browser" — and lib/notify/watch-confirmed.ts Stage 9 ships this — but no one has actually run the cold-start clock. The artifact is measurable; the measurement has not happened. Acceptance #2 is "passing-pending-observation," which is not the same as passing.** Third break, smaller: the AOI detail page renders the map *plus* a literal-text bbox line two lines above the map — leftover redundancy from before the map shipped. A real LTA newsletter reader will read both and ask which to trust. Cut the text bbox now that the map is authoritative. The brief-page snooze/pause/unsubscribe flow works only via email (no in-app analog of the four actions on the dashboard); a logged-in user who wants to pause from the dashboard has to hit the rules form, which is a thicker control than they need.

## 3. Feature audit

**Built but unnecessary:**
- users.gemini_api_key_enc column + hasByoKey field on /api/me is dead schema — no UI mints, decrypts, or even reads it for logic. The brainstorm flagged this honestly (pm/research-log/2026-05-07-v1-stop-line.md section 5b). At launch with zero users it serves no one. Drop the API surface and the column from the migration before launch; restore in v1.1 if BYO becomes a real cost lever (it will not at <50 users).
- app/dashboard/aoi/[id]/page.tsx:62-64 literal-text BBox printout is now redundant with the rendered map. Cut.
- The four-action token system (snooze + pause + unsubscribe + feedback). Snooze/pause/unsubscribe are SPEC US-5 acceptance — keep. Feedback is reviewer-recommended polish. It is shipped, validated, hardened (PRs #408, #409). Not unnecessary, but: the team spent three security-hardening chores on a path with zero users. Stop hardening it until anyone has clicked it.
- Public share-token flow (lib/share/token.ts, app/brief/share/[token]/page.tsx). SPEC US-6 use case (grant reports). Real but second-interaction. The brainstorm pushback is correct: if anything had to slip from v1, this would be it. It has not slipped — it shipped first — so this is a process observation, not a cut recommendation now.

**Missing but needed:**
- **A measured cold-start.** The plumbing is there; the observation is not. This is acceptance #2's blocker now, not the code.
- **A real prior-events corpus.** fetchPriorEvents against own-DB only means launch-day briefs structurally cannot carry the thesis's most load-bearing field. MTBS (US, free GeoJSON perimeters back to 1984) is the obvious first plug — single-archetype scoped, free, no key, fits the cron-load-once-on-AOI-create pattern. Without this, the LTA newsletter reader's first brief reads thinner than the SPEC sample paragraph.
- **ICNF/Mediterranean perimeter source.** Blocker-listed correctly; not fixable without Vanyo. v1 NA-only is defensible if launch is LTA-only; the moment outreach #1 (WWF Portugal in pm/outreach-plan-v1.md) is contacted, this becomes urgent.
- **Weather note.** lib/ai/schema.ts has weather_note; the orchestrator passes null. Open-Meteo is one tool-call, no key, free. The weather research note (chore/research-weather-context) catalogued options without picking one. Pick one. The brainstorm "thesis-honest" frame is right that *either* perimeter-everywhere *or* weather-everywhere is needed; today neither is true outside NA.
- **An in-dashboard feedback channel** beyond the email link. Power users on /dashboard cannot tell you a brief was useful. Asymmetric — only email-arriving users have the affordance.

**Built but underdeveloped:**
- **The map.** It is there, it works, it renders polygons + detections. But: (a) demo basemap (demotiles.maplibre.org) shows continent-level cartography only; at zoom 12 the LTA preserve sits on a near-blank tile. A land trust steward expects to see roads, terrain, parcel boundaries — the basemap should be a free Carto/Stadia Maps style or OSM raster. (b) No layer toggle. (c) No legend explaining the red dots' size = FRP. (d) No click-to-inspect on detections. The map ships; it does not explain.
- **pm/launch-readiness.md** is already stale relative to what merged: its row #2 narrative still says "watch confirmed... still does not fire" while its preamble says "Stage 9 brief landed." Stage 9 *code* merged after the file was written; nobody updated the table. The "single source of truth" is two-faced.
- **Backfill on first AOI** (Stage 9) catches matches but writes them through the same brief-generator + dispatcher path as cron — meaning a backfill-found brief will arrive seconds after the watch-confirmed email. There is no UX distinction ("here is an immediate brief because we found something in your last 24h"); the user gets two emails close together with no framing.

## 4. Strategic blind spots

**The 5.5 dispatcher follow-up culture.** Three different "fix dispatcher" chores merged today (#400, #408, #409, #412, #413). All defensible individually. Pattern: the team simplifies, then immediately re-hardens. lib/notify/dispatch.ts went 587 -> 426 LOC and is still the largest non-cron file. There is no test of "does a real Resend call with a real signed token actually pass the four-action footer through Gmail/Outlook spam filters" — only unit assertions about strings. Hardening without observation is over-fitting.

**ADR 0007 (Vanyo out of merge gate) — observability.** PR #422 merged with one self-review LGTM from Ent7opy (the same human as Vanyo, but the LGTM was written by the dev agent, not a separate adversarial reviewer agent). The review body is a mechanical correctness checklist: "idempotency check verified," "matcher additive," "after() throws fall-back is fire-and-forget." Zero adversarial questions. No "what happens if Vercel terminates the function before after() resolves" — the file's own comment acknowledges this as a known risk and the LGTM did not push back. No "what does the user see if watch-confirmed sends but backfill 500s." The reviewer agent is operating as a code-correctness checker, not a critic. That is a single point of failure, and the prior product review flagged exactly this risk.

**Launch-readiness and stop-line drift.** The brainstorm (pm/research-log/2026-05-07-v1-stop-line.md) explicitly framed the choice between "pre-flight" and "thesis-honest" stop-lines. The team then shipped Stage 9 (which the brainstorm recommended) without anyone explicitly committing to either frame. Stage 9 closes pre-flight; nothing closes thesis-honest. The implicit operating frame is still "ship every reviewer recommendation." That is a recipe for a v1.4 disguised as a v1.0.

**Distribution stays a single point of failure.** Outreach plan v1 names three orgs (WWF Portugal, EUROPARC, IJNR) and explicitly waits 14/21/28 days post-launch to contact them. If LTA WRN newsletter slot is delayed (newsletters have editorial calendars), v1 sits in launched-but-unwitnessed limbo for a month. No interim "is anyone reaching this" plan beyond the newsletter.

**No competitor monitoring.** Still nothing in pm/signals/ tracking Watch Duty / Technosylva product news since 2026-04-21. WD added a polygon-watch feature in the last month? Nobody would know.

**Vercel Hobby blocker still unresolved.** pm/blockers.md carries it as 2026-05-07 active; no evidence Vanyo has emailed. Acceptance #10 cannot pass without it. This is the single thing most blocking actual launch and it has no ETA.

**The brainstorm explicitly recommended cuts (BYO key plumbing, share-token de-prioritization) and nothing has been cut.** The team only adds.

## 5. Recommendations

1. **Investigate (this week):** run the cold-start clock on a clean browser with a real LTA-style polygon (pick a public Nature Conservancy preserve GeoJSON). Time the watch-confirmed email arrival. Time a synthetic FIRMS-driven backfill brief if possible. This is the single observation that flips acceptance #2 to passing or surfaces real bugs. **Stop coding more Stage 10 features until this is run.**

2. **Cut (1-line):** remove the literal-text BBox line from app/dashboard/aoi/[id]/page.tsx:62-64. Map is authoritative.

3. **Cut (small):** remove users.gemini_api_key_enc references from app/api/me/route.ts and stop returning hasByoKey. Leave the column in schema (cheap) but stop surfacing dead state. Per ADR 0006 a v1.1 stage can re-add when there is a UI.

4. **Add (small, thesis-load-bearing):** wire weather_note to a single Open-Meteo tool-call in lib/ai/generate.ts. No key, free, current-conditions endpoint is one HTTP call. Same build-without-blocking pattern as lib/ai/authority/fetch.ts (any failure -> null, brief ships). This is the cheapest single move toward thesis adherence and the brainstorm's "thesis-honest" frame.

5. **Add (medium):** plug MTBS perimeters as a static prior_events corpus for US AOIs. Load on AOI creation (one PostGIS spatial query against pre-loaded MTBS, store the matches as synthetic aoi_events rows or a separate aoi_prior_events table). Without this, every new LTA AOI's first brief structurally cannot carry the thesis's most load-bearing field. EFFIS for Europe is the v1.1 follow-up.

6. **Reframe:** lock the stop-line. The brainstorm offered two frames; the team needs to commit to one in an ADR before Stage 10 starts. Recommend pre-flight + (4) above (weather) as the thesis-honest minimum. Without this, "is v1 done" remains unanswerable.

7. **Reframe:** rewrite pm/launch-readiness.md after Stage 9. Row #2's narrative is wrong. Either flip to passing-pending-observation or split status into code-ready/observed.

8. **Add (process, not code):** make the reviewer agent adversarial. The PR #422 LGTM is mechanical. A reviewer that *only* says "tests pass, idempotency hash verified" is a linter with prose. Brief the reviewer agent to push back on at least one design choice per PR — even if the dev agent disagrees, the friction is the point. **This contradicts ADR 0007's framing of reviewer-as-replacement-for-Vanyo if reviewer remains rubber-stampy.** Either reviewer becomes adversarial or Vanyo re-enters the gate for stage PRs >= Stage 10.

9. **Investigate (Vanyo-actionable):** Vercel Hobby clause. Still on pm/blockers.md since 2026-05-07. Has been the same single line of "send sales email" for the entire pivot. The only thing more important than launch infra clarity is a measured cold-start. Both can happen in parallel.

10. **Cut (process):** stop hardening lib/notify/dispatch.ts and the four-action token system until at least one non-Vanyo human has clicked one of those links. Three hardening chores in 24h on a path with zero users is over-fitting.
