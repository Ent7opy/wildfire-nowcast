# Brief 17 — Stage 3: brief generation (AI Gateway, structured output)

## Why this exists

Stage 3 of the A' pivot. This is the stage where the product *becomes the
product* — every prior stage was scaffolding to put a polygon next to a
detection. Stage 3 turns a `(aoi, matched detection cluster)` pair into the
deliverable a stewardship user actually receives: a structured *situation
brief* generated by an LLM through Vercel AI Gateway, validated against a
Zod schema, persisted to `aoi_briefs`. It is the LLM-leverage layer the A'
thesis is built on (per `pm/north-star.md` and ADR 0005).

## Goal

Land — on a `stage-3-brief-generation` branch off `master` — the schema
table for briefs, the LLM gate (Flow 6), the structured-output prompt and
client that talks to Vercel AI Gateway → Gemini 2.5 Flash-Lite, the

## Scope (strict)

### Schema additions (new migration `db/migrations/0002_stage3.sql` + Drizzle schema)

Per `docs/pivot-architecture.md` §3 table 3.6, add:

- **`aoi_briefs`** — one row per generated brief. Columns: `id uuid pk`,
  `aoi_id uuid fk → aois`, `event_id uuid fk → aoi_events ON DELETE SET NULL`,
  `model text` (e.g. `"gemini-2.5-flash-lite"`), `prompt_version text`
  (pinned per file in `lib/ai/prompts/`, e.g. `"v1"`), `payload jsonb`
  (validates against the v1 Zod schema; binding shape from
  `docs/SPEC-A-prime-v1.md` §LLM brief format), `markdown text` (rendered
  email/UI body), `cost_usd_est numeric(10,6) null`, `latency_ms integer null`,
  `gate_reason text` (which gate condition fired — see "LLM gate" below),
  `created_at timestamptz default now()`. Index on
  `(aoi_id, created_at desc)`.

Also add a `last_brief_at timestamptz null` column on `aoi_events` so the
matcher can short-circuit dedupe-window UPSERTs that have already been
briefed (used by the gate; see "LLM gate" below).

Hand-author the SQL (same pattern as Stages 1 + 2 — `0002_stage3.sql` for
Neon, `0002_stage3.test.sql` for PGlite). PostGIS-specific syntax is not
needed here. Update `db/schema/index.ts` with the Drizzle definitions and
remove the "DEFERRED to later stages" comment for `aoi_briefs` while leaving
`notifications_log` deferred.

### LLM gate (`lib/ai/gate.ts`)

Pure TS function — no DB writes, no AI calls. Decides whether a given
`(aoi, aoi_event, recent_history)` triple should produce a brief.

Per `docs/SPEC-A-prime-v1.md` Flow 6, gate **passes** when **any** of:
- First detection for this AOI in the last 72 h (prior-absence signal).
- ≥ 2 pixels inside the alert buffer in the current event.
- Any detection with FRP > 5 MW (or the AOI's `min_frp_mw` if higher) inside the buffer.
- Any detection within 0.5 × `aoi_rules.distance_buffer_km` (close-in proximity).

Gate **fails** otherwise. The gate also rejects when:
- The matching `aoi_events` row already has `last_brief_at` set within the
  last 24 h *for the same dedupe_hash* (no double-briefing the same event).
- `aoi_rules.paused_until` is in the future.

The gate returns `{ pass: true; reason: GateReason }` or
`{ pass: false; reason: GateReason }` where `GateReason` is a string-literal
union covering all branches. Every branch is unit-tested.

### Prompt + schema (`lib/ai/schema.ts`, `lib/ai/prompts/v1.ts`)

- `lib/ai/schema.ts` exports a Zod schema **identical to**
  `docs/SPEC-A-prime-v1.md` §LLM brief format. Field-by-field. Pinned at
  `schema_version = 1`. Export both the Zod object and the inferred TS type
  (`BriefPayload`).
- `lib/ai/prompts/v1.ts` exports the system prompt and user-message
  template. Pinned, checked into the repo, version string `"v1"`. Includes:
  the AOI name + area_ha, the event details (distance, bearing,
  detection_count, peak_frp, satellites, time window), `prior_events` from
  the last 5 years pulled from `aoi_events` (max 3, most-recent first;
  may be empty), and an explicit "uncertainty" instruction matching the
  spec's `uncertainty` field requirement.
- The prompt MUST instruct: "If you do not know a value, set it to null —
  do not invent." This is the AGENTS.md no-fabrication invariant pushed
  through to model behaviour.
- `bearing_from_aoi_deg`, `nearest_detection_km` and other numerics MUST be
  computed in TS *before* the LLM call and passed in — the LLM does not
  re-derive geometry.

### AI Gateway client (`lib/ai/client.ts`)

- Use the Vercel AI SDK (`ai` + `@ai-sdk/google`) routed through AI Gateway
  (`AI_GATEWAY_API_KEY`). Use `generateObject` with the v1 Zod schema for
  structured output. Default model: `"google/gemini-2.5-flash-lite"`.
- `generateBrief({ aoi, event, priorEvents, model? })` returns
  `{ payload, model, latencyMs, costUsdEst, promptVersion: "v1" }` on
  success or a typed error on failure (`config_missing`, `validation_failed`,
  `rate_limited`, `provider_error`).
- Reads `AI_GATEWAY_API_KEY` from `process.env` lazily — function returns
  `{ ok: false, code: "config_missing" }` if missing (does not throw at
  import time; build-without-blocking, same shape as `lib/firms/client.ts`).
- On schema-validation failure: log the gate miss to `job_runs.error`, do
  NOT persist a `aoi_briefs` row, do NOT throw. Per spec acceptance #4,
  schema-failing responses are gate misses, not deliveries.
- Test-injection point analogous to `_setTestFirmsFetch` in
  `app/api/aoi/poll/route.ts` so integration tests can stub the call without
  a DI framework.

### Markdown renderer (`lib/ai/render.ts`)

- `renderMarkdown(payload: BriefPayload, aoi: AoiSummary): string` — turns
  the structured payload into the email/UI body. Leads with `summary`,
  shows `key_facts` as a compact table, prose-renders `context`, bullets
  the `recommended_watch_items`, italicises `uncertainty`, footers with
  `next_brief_hint`. Pure function, easy to snapshot-test.
- Snooze/pause/unsubscribe links are *not* added at this layer — Stage 4
  owns notification dispatch and signed tokens. The renderer outputs the
  brief content only.

### Brief-generation pipeline (`lib/ai/generate.ts`)

Single orchestrator that the poll route calls per matched event:

1. Load AOI + rules + event + last-5-year `aoi_events` for this AOI.
2. Run `gate(aoi, event, recentHistory)`. On fail, return `{ generated: false, reason }`.
3. Build prompt context (TS-computed numerics + history).
4. `await generateBrief(...)`.
5. On success: validate payload against Zod schema (already done by
   `generateObject`, but defence in depth — a re-parse before persistence).
6. Render markdown.
7. INSERT a `aoi_briefs` row in a transaction with an UPDATE setting
   `aoi_events.last_brief_at = now()` on the triggering event.
8. Return `{ generated: true, briefId, payload, markdown }`.

This function is the **only** way Stage 3 produces briefs. Both the route
hook and Stage 4's notification dispatcher consume its return shape.

### Hook into the existing poll (`app/api/aoi/poll/route.ts`)

After `matchDetectionsToAois` returns its `MatchResult`, for each event in
`eventsCreated` (i.e. status `'new'`, not updates), call `generateBrief`
through `lib/ai/generate.ts`. Add the per-bucket counts to the
`BucketRunOutcome` type:
- `briefsGenerated: number`
- `briefsGated: number` (gate-fail count, per-reason rolled up)

Update the parent `job_runs` row with totals via a new column
`briefs_generated integer not null default 0` (add to the migration).
Per-bucket gate-fail counts go into `job_runs.error` text only when at
least one bucket actually errored — gate fails are not errors, they're
expected outcomes.

If `AI_GATEWAY_API_KEY` is unset, `generateBrief` returns `config_missing`
and the route logs a single warning per poll (not per bucket) and
continues — Stage 2's matcher output is still persisted; only the brief
step is skipped. The bucket outcome reports `briefsGenerated: 0` and a
`briefSkipReason: "config_missing"` field.

### New optional API surface — defer

Per `docs/SPEC-A-prime-v1.md` §API surface, `GET /api/brief/{id}` and
`POST /api/brief/generate` are listed. **Stage 3 does NOT add HTTP
routes** — the brief generator is internal-only, called from the poll. The
HTTP routes land in Stage 5 (UI) where there's a consumer for them.
Stage 4 (notifications) reads briefs directly from the DB.

### Tests

Two layers, mirroring Stage 2's split:

1. **PGlite unit tests** for the parts that don't need PostGIS:
   - `tests/ai/gate.test.ts` — every gate branch: prior-absence, ≥2 pixels,
     FRP threshold, close-in proximity, paused, already-briefed, and
     all-fail. Pure function, no DB.
   - `tests/ai/render.test.ts` — snapshot test of the markdown for a
     canonical fixture payload (the Spring Creek example from the spec is
     a good fixture; type it in verbatim from `docs/SPEC-A-prime-v1.md`).
   - `tests/ai/schema.test.ts` — round-trip a fixture object through the
     Zod schema; assert one missing field rejects, one wrong type rejects.
   - `tests/ai/generate.test.ts` — stub `generateBrief`, run against
     PGlite-backed AOI + event fixtures, assert the `aoi_briefs` row is
     written with the right `model`, `prompt_version`, `payload`, and that
     `aoi_events.last_brief_at` is updated atomically.

2. **`@testcontainers/postgresql` integration tests** for any flow that
   touches PostGIS (none in Stage 3 strictly — the brief pipeline operates
   on already-matched events — but if you need spatial queries for
   `priorEvents`, those go here):
   - `tests/ai/generate.integration.test.ts` — full poll-to-brief flow:
     seed AOI + industrial mask, feed synthetic detections, assert one
     brief row exists with valid Zod payload, assert a second poll on the
     same event does NOT create a second brief (gate's already-briefed
     branch).

3. **Live AI Gateway test — gated.** A single integration test
   `tests/ai/generate.live.test.ts` that hits real AI Gateway runs only
   when `AI_GATEWAY_LIVE=1` is set in the environment. It is `it.skip`'d
   otherwise. CI does not set this var. Vanyo runs it locally to spot-check
   the real prompt produces a schema-valid response. The test asserts:
   schema validity, all required fields populated, no NaN/Infinity in
   numerics, latency < 30s, cost estimate < $0.01.

Add a `vitest` filter or env-gated suite as in Stage 2; default `pnpm test`
runs everything except the live test.

## Build-without-blocking discipline (per ADR 0006)

`AI_GATEWAY_API_KEY` is already set on Vercel per resolved blocker
(2026-05-06). The build still must be safe if the key is **not** reachable
(local dev without `.env.local`, ephemeral CI, key revocation):

- `lib/ai/client.ts` returns `{ ok: false, code: "config_missing" }` when
  the env var is unset — never throws at import.
- `app/api/aoi/poll/route.ts` continues to run (matching, persisting
  detections + events) and reports `briefSkipReason: "config_missing"` per
  bucket if the key is missing; the poll's overall status is still `'ok'`
  because matching succeeded.
- All non-live tests must pass without `AI_GATEWAY_API_KEY` set.
