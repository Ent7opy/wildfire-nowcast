## 2. The stop-line question

What is the smallest surface that lets a non-Vanyo first user (a named LTA WRN steward, archetype 1 per `docs/SPEC-A-prime-v1.md` line 6) complete a useful end-to-end interaction such that the LTA-WRN newsletter post (acceptance #9, brief 13) is not embarrassing? Concretely, the journey is: open landing page → recognize positioning → sign in (Clerk) → reach `/dashboard/aoi/new` → produce a polygon (now possible via paste/upload + draw, post-Stage 7) → AOI persisted → cron tick fires within 15 min → if a real FIRMS detection touches the polygon, gate evaluates and a brief is generated, validated, dispatched → user reads the brief in email or `/dashboard/brief/[id]`, finds it useful for *their place*, can snooze/pause without logging in. Today, every step in that journey has code on `master` *except*: (a) no "watch confirmed" email on AOI creation (Flow 1 step 5 — `pm/launch-readiness.md:22` confirms; grep for "first.?poll|watch.?confirmed" returns no `app/` hits), (b) no backfill on first AOI (Flow 1 step 6), and (c) the brief's `prior_events` is sourced only from this DB's own `aoi_events` history (`pm/product-reviews/2026-05-07.md:50`), so the *first* user's *first* brief on a never-burned-here-before AOI gets "no prior events on file" — the most thesis-load-bearing field reads as empty exactly when the user is forming their first impression.

## 3. Things that look done but aren't

`pm/launch-readiness.md:36-38` lists five items that cannot pass before launch by definition: #3 infra cost over 7 days, #5 P95 latency, #6 gate-pass-rate ≤ 8%, plus #1 (real LTA user) and #9 (newsletter). Items 3/5/6 are launch-week metrics — the only honest pre-launch state for them is "instrumented and queryable," which Stage 8's `data_freshness` plumbing partially supports but a derived `gates_evaluated`/`briefs_generated` count on `job_runs` (review #6) is not in `master` yet. Items #2 and #8 are now arguably passing post-Stage-7 + post-LICENSE — `pm/launch-readiness.md` was last written before PR #406/#407 merged, so the doc itself is drifted; the next `pm` turn should re-walk it. The deeper point: once we accept "we cannot self-validate items 3+5+6 before launch," the stop-line stops being "all 10 acceptance items pass" and starts being "the 1–2 + 4 + 7–8 + 10 subset passes, and 3 + 5 + 6 are *instrumented* such that launch-week observation is feasible." That re-frame matters because otherwise the team will keep adding code in pursuit of a green dashboard that cannot exist pre-user.

## 4. v1.1 items that arguably move to v1

- **ICNF authority adapter.** Stage 8 (PR #411) shipped NIFC + CWFIS, NA-only. The thesis explicitly names Mediterranean Natura 2000 site managers as archetype 3 (`docs/SPEC-A-prime-v1.md:6`) and `pm/product-reviews/2026-05-07.md:80` (§5 #5) calls authority perimeter "the single highest-leverage move for thesis adherence." If LTA WRN is the v1 distribution, NA-only is fine. If the second-archetype outreach plan (Stage 8 §11) opens any Mediterranean door before launch, ICNF should ride along — otherwise the second archetype's first brief is `authority_perimeter: null`, the same templatey state v1 was supposed to cure.
- **Weather context fetch.** `lib/ai/schema.ts` has `weather_note`; Stage 3 (`pm/briefs/17-stage3-brief-generation.md`) hardcoded null; nothing has revisited it since. The thesis's own sample paragraph leans on fuel/weather context. Without weather, the brief is "AOI + detection + maybe-perimeter + maybe-prior-events" — measurably thinner than the SPEC sample. Argument for v1: it's a single tool-call (Open-Meteo, free, no key). Argument against: another network dep on the cron's hot path, and `data_freshness` semantics need extending.
- **Backfill on first AOI.** Flow 1 step 6 in SPEC. Today a user who creates an AOI mid-fire waits up to 15 min for the next cron tick and may miss a detection that fired 13 min ago. This is the single largest UX cliff on the cold-start path; it directly competes with US-1's 5-min SLA. Strongly argue v1.
- **"Watch confirmed" / "first poll scheduled" email.** Acceptance #2's *terminal event* — without it, the 5-min SLA is unmeasurable. `pm/launch-readiness.md:22` already flagged this as a "small follow-up chore" out of Stage 7 scope. It's a one-route chore on top of the dispatcher; v1.

## 5. v1 items that arguably move out

Push back on the team's own shipping. (a) **Share-token public-link flow** (`lib/share/token.ts`, public share page) maps to SPEC US-6 (grant-report exports) — a real archetype-1 use case but not a *first-interaction* one. A steward needs to read one brief before they need to share one. Could ship in v1.1 with no thesis cost. (b) **`users.gemini_api_key_enc`** is in schema (`db/schema/index.ts`) and referenced in Stage 5/6 briefs but no UI surfaces it. BYO-key is a cost-mitigation knob for *after* AI Gateway free-tier saturation; pre-launch with zero users it's dead schema. Argue cut from v1 — leave the column, drop any UI hook. (c) **Four-action email token system (snooze + pause + unsubscribe + feedback)**. Snooze/pause/unsubscribe are SPEC US-5 acceptance and load-bearing. Feedback ("did this brief help?") came from `pm/product-reviews/2026-05-07.md:82` (§5 #6) and is genuinely valuable, but it's the lowest-criticality of the four — if any one of these is going to bug, feedback breaking is the lowest cost. Keep it (already shipped) but de-prioritize hardening.

The honest pushback on §4: if §5 is right that the team has overbuilt some surface, then the §4 additions (weather, ICNF, backfill, watch-confirmed) total roughly the same code volume as the §5 cuts. The framing is not "ship more"; it's "ship the right less." A v1 that has backfill + watch-confirmed-email but no public-share page is closer to the thesis than the inverse.

## 6. Recommended frame for the next decision

Do not let the stop-line be set by "all 10 acceptance items green." That criterion is unreachable pre-launch by construction (items 3/5/6) and the team will burn cycles chasing it. Instead, the next product-reviewer or `pm` synthesis pass should pick *one* of these two frames and commit:

1. **"Pre-flight" frame.** Stop-line = acceptance #1, #2, #4, #7, #8, #10 passing; #3, #5, #6 instrumented-and-queryable; #9 drafted-and-held. Adds to v1: watch-confirmed email + backfill on first AOI + a `gates_evaluated` counter for #6 to be queryable. Defers to v1.1: weather, ICNF, share-page polish. Risk: ships without observed thesis-adherence on the brief itself.
2. **"Thesis-honest" frame.** Stop-line = pre-flight frame + at least one non-null `authority_perimeter` *or* `weather_note` path on every brief, so the launch-week first user does not see an empty thesis. Adds to v1: weather (cheaper than ICNF) *or* ICNF (more thesis-aligned for Mediterranean). Risk: 1–2 weeks of additional work and another network dep on the cron hot path.

Either is defensible. The frame the team has *implicitly* been operating in is "ship every reviewer recommendation," which is not a stop-line at all. The single most important thing to surface to the next decision-maker is that **the missing piece on the cold-start path is not the map (shipped), the snooze tokens (shipped), the LICENSE (shipped), or the perimeter (NA-shipped) — it is the watch-confirmed email plus first-AOI backfill, neither of which is in `master`, both of which gate acceptance #2's measurability, and together they are smaller than any single shipped stage.**

If only one thing gets done before the launch decision is made, it is those two.
