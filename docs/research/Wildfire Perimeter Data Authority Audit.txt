Technical Audit of Wildfire Geospatial Intelligence and Global Perimeter Promotion Logic
The development of a high-fidelity wildfire denoiser requires a rigorous engineering framework to distinguish between transient operational noise and authoritative administrative truth. In the geospatial domain, a fire perimeter is not a static geometry but a dynamic record governed by agency-specific protocols, technical schemas, and validation gates. The primary objective of this technical audit is to define the exact criteria and API architectures necessary to implement an "Authoritative Perimeter Promotion Gate." This gate serves as the decision-making engine that promotes inbound geospatial data from a "Monitoring Tier" (Bronze) to an "Operational Tier" (Silver) and, finally, to a "Certified Ground Truth" (Gold). By refusing the ingestion of unverified polygons or dummy data, this system ensures that only incident-command-approved data points inform the operational model.
I. Primary Authority (USA): NIFC WFIGS/NIFS Governance and Data Lifecycle
The National Interagency Fire Center (NIFC) is the central authority for wildland fire data in the United States. Through the Wildland Fire Interagency Geospatial Services (WFIGS) group, authoritative data products are distributed to federal, state, and local agencies.1 The core of this system is the Integrated Reporting of Wildland Fire Information (IRWIN) service, which brokers data between disparate applications to ensure consistency and eliminate redundancy.3
1. Integrated Reporting of Wildfire Information (IRWIN) Mechanics
The IRWIN service is the "system of record" for incident attributes, which are then synchronized with geospatial geometries in the National Incident Feature Service (NIFS). IRWIN operates as a RESTful web API that allows authenticated systems to perform Add, Query, and Update operations.3 For a perimeter to be promoted, it must first be valid within the IRWIN integration service. IRWIN supports conflict detection and resolution to ensure a unique record for each incident.5 If an incident is identified as a duplicate, it may be quarantined or deprecated, which immediately impacts its visibility in public geospatial services.1
Systems interacting with IRWIN are assigned specific roles. The IRWINREAD role is utilized by systems that only consume data, while IRWINCAD and DISPATCH roles allow for write actions from Computer-Aided Dispatch systems.3 A critical component for the promotion gate is the Authoritative Data Source (ADS) matrix. This matrix defines which system has the primary authority over a specific attribute at a given time.3 During the initial attack and active growth phases, the ADS for a perimeter is typically the NIFS; however, once the fire is contained and the final fire report is certified, the ADS transitions to InFORM (Interagency Fire Occurrence Reporting Modules).5
2. The National Incident Feature Service (NIFS) Geospatial Schema
The NIFS is a hosted feature service within NIFC's ArcGIS Online organization. It implements the NWCG Wildland Fire Event Polygon standard (PMS 936).8 This standard ensures that perimeters from diverse agencies—such as the US Forest Service (USFS), Bureau of Land Management (BLM), and National Park Service (NPS)—are interoperable.8 For the denoiser, the most critical layers are the Wildfire Daily Fire Perimeter and the Wildfire Final Fire Perimeter.8

II. Infrastructure Governance and API Performance Constraints
In the context of mission-critical engineering, the infrastructure hosting the data is as significant as the data itself. NIFC utilizes the ArcGIS Online host services3.arcgis.com. Interacting with this host at high frequencies (e.g., for real-time alerting) requires strict adherence to organization-wide performance rules.
1. Rate Limiting and Request Units (RU)
ArcGIS Online subscriptions enforce limits based on "Request Units" (RUs). RUs are not a simple query count; they represent a cumulative "weight" based on the load the query puts on the Feature Data Store.29
* Standard Organizations: Shared limit of approximately 10,000 RUs per minute.29
* Premium Data Stores (M2/M4): Higher capacity, up to 96,000 RUs per minute, with dedicated database processing power.29
* Error Handling: When the organization's limit is reached, the server returns a 429 (Too Many Requests) error. A one-minute "cooling off" period is triggered during which non-cacheable queries are rejected.29
2. Polling Strategy and Latency Management
Data in WFIGS is refreshed from IRWIN every 5 minutes.1 However, there is an additional latency for the source polygon updates to appear in the public portal, which can take up to 15 minutes.1
The coding agent must implement the following polling discipline:
* Minimum Polling Interval: 10 seconds. ArcGIS Velocity and other polling-type feeds enforce this to prevent overloading the feature service.33
* Cache Utilization: To avoid 429 errors, queries must be designed to be cache-repeatable. This means avoiding the use of CURRENT_TIMESTAMP or "in the last X days" filters within the SQL WHERE clause, as these force the system to bypass the Content Delivery Network (CDN) and query the source database directly.23
* Refresh Intervals: For web applications, a "refresh interval" property can be set on the layer to sync automatically with the latest data while the map is open. The valid range for hosted feature layers is 0.5 minutes (30 seconds) to 1 day.34
3. API Key and Authentication Requirements
While the WFIGS services are public, high-frequency access or integration with secure resources may require API Key authentication. API keys are long-lived access tokens (valid for up to one year) that can be scoped to specific services.36 They are the recommended type of authentication for standalone automation scripts that perform operations with a personal scope.37 For public-facing web applications, storing credentials with the service item allows the public to access secure services via an ArcGIS item proxy without signing in.39
III. Secondary Authority (Canada): CWFIS and the Completeness Lag
The Canadian wildland fire geospatial ecosystem, managed by the Canadian Wildland Fire Information System (CWFIS), differs significantly from the US model. While CWFIS provides a national view, the authoritative data is collected at the provincial and territorial levels by agencies such as the British Columbia Wildfire Service and Alberta Wildfire.41
1. Completeness Lag and Approval Stages
There is a documented "completeness lag" in the Canadian National Fire Database (CNFDB). This database is a collection of forest fire perimeters projected into a common format, but data accuracy and quality vary among contributing agencies and between years.43
* Estimated/Rough (Bronze): These are "Fire Perimeter Estimates" generated from satellite-detected hotspots in near-real time (e.g., MODIS/VIIRS). These approximate burned area perimeters are considered very rough and are intended primarily for large fires when no other mapping options exist.42
* Agency Approved (Silver): During the fire season, provinces provide reported active fire locations updated daily.42 These are operational estimates but are not "final."
* Certified Truth (Gold): The National Burned Area Composite (NBAC) is the definitive national geospatial product. It chooses the "best available source" for each burned area, incorporating refined provincial data and satellite analysis. However, the NBAC update cycle is slow, with the previous year's fires typically finalized once a year in July.42
2. 2025 Canadian Context: The "Zombie Fire" Phenomenon
The 2025 Canadian wildfire season was heavily influenced by the extreme 2023 and 2024 seasons. By mid-June 2025, the season was on track to be the second-worst on record.47 A unique challenge for a 2025 denoiser is the presence of holdover "zombie fires"—fires that smolder under the snow for up to two years and re-emerge in the spring.47
From an engineering perspective, these fires have an ignition date in 2023 but appear as active in 2025. The denoiser must use the poly_PolygonDateTime or DATE_CUR field rather than discovery date alone to track current fire progression.1
3. CWFIS Technical Access and API Endpoints
Unlike WFIGS, Canada relies heavily on OGC-standard web services through GeoServer.
* Web Feature Service (WFS) for Vector Data: https://cwfis.cfs.nrcan.gc.ca/geoserver/wfs? 42
* Web Map Service (WMS) for Visualization: https://cwfis.cfs.nrcan.gc.ca/geoserver/wms? 42
* Downloadable Indices (SHP): Current Active Fires are available at https://cwfis.cfs.nrcan.gc.ca/downloads/activefires/.42
Promotion Rule for Canada: National data remains in the Monitoring Tier (Bronze/Silver) until the annual NBAC release. Real-time promotion to "Gold" is not technically feasible for 2025 incidents at the national level without direct provincial-tier WFS ingestion.
IV. EU and Global Authorities: EFFIS/GWIS Satellite Reality
For Europe, the Middle East, and North Africa (MENA), the authoritative monitoring system is the European Forest Fire Information System (EFFIS), part of the Copernicus Emergency Management Service (CEMS).48 A fundamental technical conclusion of this audit is that EFFIS and GWIS perimeters are purely satellite-derived and lack incident-command verification.50
1. Methodology of Satellite Delineation
EFFIS utilizes a semi-automatic procedure for mapping burned areas through its Rapid Damage Assessment (RDA) module.50
* Detection: MODIS (250m) and VIIRS (375m) sensors identify thermal anomalies ("hotspots") by comparing pixel temperature against surrounding land cover.51
* Initial Mapping: Polygons are automatically derived from the coordinates of active fires, allowing for near-real-time processing even in light cloudy or smoke situations.50
* Refinement: Since 2018, Sentinel-2 imagery (20m resolution) has been used to map fires smaller than 30 ha and refine the final perimeters of larger fires.50
* Denoising Step: Trained analysts inspect satellite imagery to delineate boundaries and perform visual interpretation to ensure non-fire heat sources (like photovoltaic installations) are not mistakenly mapped as burned areas.53
2. Copernicus EMS Rapid Mapping API
For high-intensity events, the Copernicus Rapid Mapping team produces "Activations" that provide detailed damage assessments. These activations are accessible programmatically via a JSON API.54
* JSON API Listing: https://rapidmapping.emergency.copernicus.eu/backend/dashboard-api/public-activations-info/ 54
* Activation Search: Filtering by code (e.g., EMSR833 for Greece 2025) provides full activation metadata, including Areas of Interest (AOIs) and product links.54
* Product Types:
   * DEL (Delineation Map): Provides the extent of the event.
   * GRA (Grading Map): Provides damage assessment (severity).
   * Reliability Logic: Only products flagged as feasible (cloud-free imagery available) should be ingested.54
Promotion Rule for EU/Global: No authoritative promotion source found for incident command verification in real-time. All EFFIS perimeters must remain in the Silver (Satellite-Analyst Verified) tier and never be promoted to Gold (Ground Truth).

VI. Deprecated Systems and Data Redirection
A robust denoiser must proactively exclude legacy data feeds that are no longer considered authoritative.
1. BLM FPER Deprecation
The Bureau of Land Management Fire Occurrence and History Perimeter (FPER) dataset is explicitly non-authoritative post-2019.14
* Official Redirection: Per FA IM-2020-009, management and certification of perimeters were transferred to the NIFS via NIFC.14
* Engineering Action: Flag any system using gis.blm.gov/arcgis/rest/services/fire/BLM_Natl_FirePerimeter for 2025 data as an "Invalid Source".61
2. GeoMAC Decommissioning
The legacy Geospatial Multi-Agency Coordination (GeoMAC) application has been replaced by the WFIGS services.5
* Engineering Action: Perimeter data between 2000–2018 is archived and static. All 2019 and later perimeters must be pulled from the NIFS-based WFIGS services.12

2. Geometry and Acreage Validation Logic
A significant source of noise in wildland fire data is the discrepancy between GIS-calculated area and manually reported acreage.
* Validation Rule: Cross-check poly_GISAcres against attr_IncidentSize (or attr_DiscoveryAcres for early starts).
* Denoising Heuristic: If poly_GISAcres is 0.0 or null, reject promotion. If the difference between poly_GISAcres and attr_IncidentSize is greater than 20%, flag for "Manual Review" rather than automatic promotion.18
3. Handling Size Classes for Fall-off Logic
The system should be aware that smaller fires are less likely to have perimeters. For Class A and B fires (   acres), perimeters are often not captured at all.17 The denoiser must expect a lack of polygons for these size classes and rely on the 2025 Wildland Fire Incident Locations to Date (point) service for those incidents.1
VIII. Stop/Go Statement for coding Agent Promotion
The Authoritative Perimeter Promotion Gate is authorized to promote a record to "Real World Truth" ONLY under the following conditions:
1. GO: The source is NIFC WFIGS AND poly_FeatureStatus = 'Approved' AND poly_FeatureAccess = 'Public' AND poly_IsVisible = 'Yes' AND attr_IsValid = 1.1
2. STOP: If the source is EFFIS, GWIS, or CWFIS Fire Perimeter Estimates (Satellite-derived), the record MAY NOT be promoted beyond the "Monitoring Tier" (Bronze). These records are estimates and fail the "Incident Command Approved" ground-truth requirement.45
3. STOP: If the attr_IsQuarantined flag is set to True (1) in the US source, or if a potential conflict is detected by the IRWIN broker.1
4. GO (Gold Certification): If the incident has a containment date and the poly_Source = 'FFP', it is promoted to the highest historical ground-truth tier.2

X. Causal Relationships in Operational Wildfire Data
To understand the reliability of a perimeter, one must analyze the causal relationship between discovery, resource mobilization, and geospatial reporting. The IRWIN service facilitates near-real-time synchronization between disparate agencies, but the "Truth" of a fire perimeter is a function of the tools used by the GISS (Geographic Information System Specialist) assigned to the incident.3
1. Data Inception and CAD Integration
A fire record typically originates in a Computer-Aided Dispatch (CAD) system (e.g., WildCAD) when a report is received.3 This record is pushed to IRWIN, creating a "Point" location with initial estimated acreage.5 At this stage, the fire is in the Bronze Tier. No perimeter exists, only a center point.
2. GISS Mobilization and NIFS Synchronization
Once an Incident Management Team (IMT) is assigned, a GISS is tasked with mapping the fire. They create an "Offline Copy" of the NIFS Event Polygon layer in ArcGIS Pro.11
* The Sync Cycle: The specialist performs a "Sync – Edit – Sync" workflow. Before editing, they pull the latest geometries from the server to avoid conflicts. After editing (e.g., after an overnight IR flight or a morning GPS walk), they sync their changes back to the NIFS.11
* Public Visibility: These edits are initially "Internal." Only when the SITL or GISS sets poly_FeatureAccess = 'Public' and poly_FeatureStatus = 'Approved' does the perimeter flow into the public WFIGS perimeters used by applications like InciWeb.11 This transition is the moment of promotion to the Silver Tier.
3. Post-Incident QA/QC and InFORM Certification
After the fire is declared "Out," the operational phase ends, but the data lifecycle continues. The incident record moves into the InFORM application for certification.2
* Certification Gate: A regional or local authority reviews the final acreage, cause, and final perimeter. Upon certification, the poly_Source is updated to 'FFP' (Final Fire Perimeter).2
* ADS Shift: The ADS for the record shifts from NIFS to InFORM FODR (Fire Occurrence Data Records).5 This is the final promotion to the Gold Tier.
XI. Infrastructure Performance: Detailed RU and CDN Dynamics
High-frequency polling for a wildfire denoiser can inadvertently trigger a denial-of-service state on the public feature service if query weighting is not optimized.
1. Query Weighting in ArcGIS Online
Different REST operations consume different amounts of Request Units (RUs).
* Simple Attributes: Querying basic fields (e.g., WHERE poly_IRWINID = '{...}') is low weight.
* Geometry Queries: Spatial queries (e.g., ST_Intersects) and pulling full multipart polygons are high weight.29
* Cache Misses: Queries with non-repeatable parameters (like a sliding time window) bypass the CDN cache and hit the database directly, incurring 100% of the RU cost.29
2. Mitigation for 429 Errors
To maintain a performant denoiser without hitting RU limits:
* Referrer Restriction: The API should be configured with specific Referrer URLs/IPs to ensure requests are recognized as coming from a legitimate service rather than an anonymous bot.39
* Paginated Requests: Pulling large datasets (e.g., the 2025 Full History) should be paginated. Pulling 3,000 records in one request is significantly more RU-intensive than three requests of 1,000 records each.29
* Webhook Alternatives: While not always available for public feeds, checking the lastEditDate property of the service allows the denoiser to skip querying if no changes have occurred since the last poll.
XII. Global Perspective: Regional Limitations and Authenticity
The audit confirms that while the US and Canada have structured (though lagged) authoritative systems, other global regions rely heavily on satellite estimates.
1. EFFIS/GWIS Regional Accuracy
EFFIS coverage represents about 95% of the total burned area in the EU.50 However, the spatial resolution of the original EFFIS product (250m) refined with Sentinel-2 (20m) does not match the underlying Map Tiler imagery used for visualization.50
* Global Wildfire Information System (GWIS): GWIS provides a synoptic view of global fire activity but uses the MODIS burned area product (MCD64A1) as its base. This product takes approximately two months to be available, creating a significant temporal gap for 2025 real-time monitoring.52
* Authenticity Note: In many parts of the EU, Middle East, and North Africa (MENA), there is no public-facing incident command perimeter endpoint. For these regions, the denoiser must explicitly stay in the Monitoring Tier (Bronze/Silver) and acknowledge that perimeters are estimates based on manual analyst refinement of satellite imagery.50
2. Australia and Southeast Asia (Inferred)
While not the primary focus of the US/Canada/EU audit, research into GWIS confirms that global wildfire data is "fragmented and inconsistent" outside of these major authorities.52 For Indonesia and Nepal, specific SMS alert systems exist based on FIRMS hotspots (Bronze tier), but authoritative, command-approved polygons are not identified in the public API scope.66
XIII. Final Technical Implementation Contract Summary
This document serves as the final technical contract for the build-out of the "Authoritative Perimeter Promotion Gate."
1. Direct API Integration: All inbound data must flow from the WFIGS and CEMS Rapid Mapping REST endpoints. Legacy BLM and GeoMAC sources are strictly deprecated.
2. Logic over Heuristics: Promotion decisions must be binary metadata matches (poly_FeatureStatus = 'Approved'). There is no "guessing" based on fire name or proximity.
3. Temporal Precision: The 2025 Window Strategy uses attr_FireDiscoveryDateTime for inclusion and poly_PolygonDateTime for progression tracking.
4. Tiered Reliability: Gold/Silver/Bronze tiers are assigned based on poly_Source and poly_MapMethod.
5. Infrastructure Health: Polling must adhere to a 10-second minimum and utilize CDN-friendly queries to avoid 429 throttling.
The "Stop/Go" definition is final. If a perimeter fails the command-approval metadata check, it remains "Operationally Unverified" and is excluded from the ground-truth model. This ensures that the wildfire denoiser operates with maximum precision, reflecting the administrative and geospatial reality on the ground during the 2025 fire season.
